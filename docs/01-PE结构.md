# 01 · PE 结构剖析

## 1. 文件头关键字段

| 字段 | 值 | 说明 |
|---|---|---|
| `e_magic` / `e_lfanew` | `MZ` / `0xF0` | DOS 头 + 0xB0 字节 stub（含 Rich 头） |
| `Machine` | `0x8664` | AMD64 |
| `NumberOfSections` | 8 | 见段表 |
| `TimeDateStamp` | `0x69E74BB4` (2026-04-21 18:04:36 UTC) | 链接时间戳 |
| `Characteristics` | `0x0022` | EXECUTABLE_IMAGE \| LARGE_ADDRESS_AWARE |
| `Magic` | `0x20B` | PE32+ |
| `AddressOfEntryPoint` | `0x46000` | 落在 `INIT` 段，即 `DriverEntry` |
| `ImageBase` | `0x140000000` | 固定基址（驱动加载时按此映射） |
| `SectionAlignment` / `FileAlignment` | `0x1000` / `0x200` | 标准内核驱动对齐 |
| `SizeOfImage` | `0x129000` | 含 `.tvm0` 全段 |
| `SizeOfHeaders` | `0x400` | 头部 1024 字节（有效结构 824 + 填充） |
| `CheckSum` | `0x124E80` | 本工程用标准算法重算，结果一致 |
| `Subsystem` | `1` | NATIVE（内核驱动） |
| `DllCharacteristics` | `0x01E0` | HIGH_ENTROPY_VA \| DYNAMIC_BASE \| FORCE_INTEGRITY \| NX_COMPAT |

> `FORCE_INTEGRITY`（`0x80`）置位：加载器会校验签名，这与本工程「必须字节全同」的约束直接相关——只有哈希一致，签名才继续有效。

## 2. 段表

| 段 | RVA | VirtualSize | RawPtr | RawSize | 特征 | 内容 |
|---|---|---|---|---|---|---|
| `.text` | `0x001000` | `0x2D87C` | `0x000400` | `0x2DA00` | code+exec+read | 34 个可用函数主体、42.5k 条指令 |
| `.rdata` | `0x02F000` | `0x0592C` | `0x02DE00` | `0x05A00` | init+read | IAT（`0x2F000`，0x2A0）、LOADCFG、调试目录、少量常量 |
| `.data` | `0x035000` | `0x0C402` | `0x033800` | `0x00400` | init+read+write | 只有 0x400 字节有初值，其余 0xC002 是 BSS 尾部 |
| `.pdata` | `0x042000` | `0x03084` | `0x033C00` | `0x03200` | init+read | **1,035 条** RUNTIME_FUNCTION（`.text` 1034 + `INIT` 1） |
| `INIT` | `0x046000` | `0x00ACA` | `0x036E00` | `0x00C00` | code+exec+read+discardable | `DriverEntry` 与初始化例程 |
| `.rsrc` | `0x047000` | `0x003F0` | `0x037A00` | `0x00400` | init+read+discardable | 版本资源 |
| `.reloc` | `0x048000` | `0x00094` | `0x037E00` | `0x00200` | init+read+discardable | 基址重定位（仅 1 个块） |
| `.tvm0` | `0x049000` | `0xE0000` | `0x038000` | `0xE0000` | code+exec+read | **TVM 保护载荷**（见 docs/03） |

文件布局是紧凑的：`0x400 + 0x2DA00 + 0x5A00 + 0x400 + 0x3200 + 0xC00 + 0x400 + 0x200 + 0xE0000 = 0x118000`，其后是 0x52B0 的 Authenticode blob，一直到 EOF（`0x11D2B0`）。所有 raw 指针都是 `0x200` 的整数倍，说明这就是 link.exe 的正常输出（不是后期加壳重排）。

## 3. 数据目录（10 个非空）

| # | 目录 | RVA | 大小 | 备注 |
|---|---|---|---|---|
| 1 | IMPORT | `0x4605C` | `0x3C` | 2 个模块：`ntoskrnl.exe`（81）+ `HAL.dll`（1） |
| 2 | RESOURCE | `0x47000` | `0x3F0` | 版本信息 |
| 3 | EXCEPTION | `0x124000` | `0x3228` | **1,070 条，位于 `.tvm0` 内部** |
| 4 | SECURITY | `0x118000` | `0x52B0` | Authenticode PKCS#7（文件偏移，非 RVA） |
| 5 | BASERELOC | `0x123000` | `0x0F70` | **184 个重定位块，位于 `.tvm0` 内部** |
| 6 | DEBUG | `0x30970` | `0x54` | CodeView 记录，PDB 名被清零 |
| 10 | LOADCFG | `0x309D0` | `0x108` | CFG 校验字段（GuardFlags 等） |
| 12 | IAT | `0x2F000` | `0x2A0` | 82 个槽位 |

注意目录 3 与目录 5 **不指向** `.pdata` / `.reloc` 段，而是指向 `.tvm0` 段尾部：
- `.pdata` 段（`0x42000`）里另有一份 1,035 条的 RUNTIME_FUNCTION 副本；
- `.reloc` 段（`0x48000`）里只剩 1 个块（`0x94` 字节），真正的 184 个块在 `0x123000`。

这是"打包后重写目录"的典型特征：TVM 打包器把**真正的**异常表与基址重定位表搬进了自己的数据段，`SizeOfImage` 也随之扩展到 `.tvm0` 末尾，让加载器直接按段映射把这段当代码使用。两份表的差集（1,146 − 1,035 = 111）正好等于 `.tvm0` 内被登记的 111 个函数。

## 5. 头部重建的可验证性

`tools/mkheaders.py` 不使用任何原始字节副本重建头部：

- `0x00..0x40`：DOS 头，14 个字段逐个 `pack_into`
- `0x40..0xF0`：DOS stub + Rich 头（工具版本向量 + XOR 校验），作为 0xB0 字节的 `db` 源（`src/asm/assets/dos_stub.asm`）
- `0xF0..`：PE 签名 + COFF 头 + 可选头（22 个字段）+ 16 个数据目录 + 8 个段头，全部按字段写入
- 剩余到 `0x400` 的填充补零

自校验结果：**1024 字节与原件 0 差异**。这条通过之后，后续任何段内字节差异都只可能来自代码/数据本身，不会与头部混淆。

## 6. 签名

| 项目 | 值 |
|---|---|
| 类型 | Authenticode / PKCS#7，位于 overlay `0x118000..0x11D2B0` |
| 大小 | 21,168 字节 |
| 主体 | `CN=Microsoft Windows Hardware Compatibility Publisher` |
| 签发 | `CN=Microsoft Windows Third Party Component CA 2014` |
| 有效期 | 2025-07-17 → 2026-07-15 |
| 重建后状态 | `Valid`（因为文件字节完全相同，摘要自然一致） |

签名块在工程里作为 `src/asm/assets/authenticode.asm`（1,323 行 `db`）参与构建，因此**整份产物没有任何未记录的二进制 blob**。
