# 08 · 信封协议与操作码表

本文把 `IRP_MJ_DEVICE_CONTROL` 的**载荷格式、编解码算法、操作码空间**全部落到可复现的字节事实。配套实现：`tools/envelope.py`（自测通过）。

---

## 1. 结论先行

| 项 | 值 |
|---|---|
| 输入缓冲长度 | **必须恰好 `0x24C`（588）字节**（`cmp [rsp+0x280], 0x24C`，长度不符直接返回 `0xC0000001`） |
| 输出缓冲长度 | `0x222824`/`0x22282C` 至少 4 字节；后续阶段要求 ≥ `0x30`（48） |
| 载荷上限 | `payload_len <= 0x200`（`cmp edx,0x200`，超限返回 `0xFFFFFFFC`） |
| 密钥 | 客户端自带 8 个 32 位轮密钥，`key = key[sel & 7]` |
| 编码 | XOR + 二次同余状态机（模 `0xDC6A2367`），见 §4 |
| 操作码 | 载荷首 dword = **`0x63AE442D + k`**（k=0..11），其中 `k ∈ {3,4,5,6,7,9,10}` 被接受 |
| 命令数 | 7 个可用操作码（12 个候选里剔除 5 个） |

## 2. 封套结构（`SystemBuffer`，0x24C）

| 偏移 | 大小 | 字段 | 事实来源 |
|---|---|---|---|
| `+0x000` | 4 | `status` / `cmd` | 返回时驱动写入：`mov dword [rbx], eax`（`0x6216C`） |
| `+0x004` | 0x20 | 保留 / token | 未被派发器直接引用（推断为客户端的会话标记） |
| `+0x024` | 4 | `payload_len` | `mov edx,[rbx+0x24]; cmp edx,0x200`（`0x61EBE`） |
| `+0x028` | 0x200 | `payload[512]` | `lea rcx,[rbx+0x28]`（`0x61F10`）作为解码源 |
| `+0x228` | 0x20 | `key[8]` | `mov r8d,[rbx+r8*4+0x228]`（`0x61F3B`） |
| `+0x248` | 4 | `key_select` | `mov r8d,[rbx+0x248]; and r8d,7`（`0x61EE0`） |
| `+0x24C` | — | 缓冲结束 | 与 `InputBufferLength == 0x24C` 完全吻合 |

> `+0x228 + (sel&7)*4` 的取值就是本轮载荷的解密密钥。8 个槽位允许客户端在一帧里携带多组密钥（例如密钥轮换/多会话），但每次只用一个。

## 3. 调用链与参数落位

```
IRP_MJ_DEVICE_CONTROL  →  sub_1700 (0x1700)
   └─ jmp 0x6CF71                       ; .tvm0 内，613 字节
        ├─ rax = [Irp+0xB8]             ; CurrentStackLocation
        ├─ r14 = [Irp+0x18]             ; AssociatedIrp.SystemBuffer  → 后面的 rbx
        ├─ esi = [Iosl+0x08]            ; OutputBufferLength
        ├─ r15d= [Iosl+0x10]            ; InputBufferLength
        ├─ ebx = [Iosl+0x18]            ; IoControlCode  →  g_LastIoctl(0x35330)
        ├─ call loc_2090                ; 门禁：g_KillSwitch(0x35650)==0
        ├─ lock xadd [g_InFlight],1     ; 0x3534C
        └─ call sub_2480 → 0x61DC6      ; 派发器（.tvm0）
```

派发器里的实参落位（与 Windows x64 调用约定对齐）：

| 位置 | 值 | 用途 |
|---|---|---|
| `r8d` | `IoControlCode` | `cmp r8d, 0x222824` 三分支 |
| `rbx` | `SystemBuffer` | 封套基址 |
| `[rsp+0x280]`（= 调用者 `+0x20`） | `InputBufferLength` | `cmp ...,0x24C` |
| `[rsp+0x288]`（= 调用者 `+0x28`） | `OutputBufferLength` | `cmp ...,4` / `cmp ...,0x30` |
| `edi` 初值 | `~0x3FFFFFFE` = `0xC0000001` | 默认返回码 |

## 4. 载荷编解码（`sub_20580`，0x20580，127 字节）

```
p       = 0xDC6A2367
state   = (payload_len * key) mod p                 ; 0x205CD: imul ecx,r8d + 魔数取模
for i in 0 .. payload_len/4 - 1:
    c        = src32[i]
    out32[i] = c XOR state                           ; 0x2062B  xor ebx,r8d / 0x2062E mov
    t        = out32[i] + c                          ; 0x20632  lea r8,[rbx+rcx]
    state    = (t*t) mod p                           ; 0x20647  imul r8,r8  + 取模
    state    = (state*state) mod p                   ; 0x2064B  mul r8     + 取模
tail (payload_len & 3) 字节                          ; 0x20679  调 memset 补 0
return 1 成功 / 0 失败                                ; 0x20686
```

取模序列：`mul 0x4A5528196BE73A81; shr rdx,0x1E; imul rdx,p; sub` —— 64 位常量除法的标准展开，等价于 `x % 0xDC6A2367`。
前置校验：`src != NULL`、`len != 0`、`dst != NULL`、`capacity >= len`，否则返回 0。

Python 参照实现（`tools/envelope.py`）：

```python
P = 0xDC6A2367
def decode(src, key):
    state = (len(src) * key) % P
    out = bytearray(len(src))
    for i in range(len(src) // 4):
        c = int.from_bytes(src[i*4:i*4+4], "little")
        w = c ^ state
        out[i*4:i*4+4] = w.to_bytes(4, "little")
        state = ((w + c) ** 2) % P
        state = (state ** 2) % P
    return bytes(out)
```

自测（本工程实测）：

```
key=0x11223344  encode!=plain=True  roundtrip=True
key=0xdeadbeef  encode!=plain=True  roundtrip=True
key=0x00000000  encode!=plain=True  roundtrip=True
```

> 注意：`state` 的更新同时用到明文与密文，所以加解密是"同一状态机、同一顺序"，两端都持有 `(src, out)` 对，天然可逆。

## 5. 操作码空间（`sub_6392E` → `0x639BB`）

驱动先解码载荷，再把载荷首 dword 当作命令字校验：

```asm
0x639BB  mov  eax, dword ptr [rbx]        ; 载荷首 dword = 命令 token
0x639BD  add  eax, 0x9C51BBD3             ; 归一化
0x639C2  cmp  eax, 0xB                    ; 必须 <= 11
0x639E0  ja   reject                      ; 越界 → 走 0x63A1D
0x639EC  mov  ecx, 0xFFFFF6F8
0x639F1  not  ecx                         ; ecx = 0x00000907
0x639F3  bt   ecx, eax                    ; 查位
0x63A11  jb   return_0                    ; 位置 1 → 静默拒绝（返回 0）
0x63A1D  call sub_2060                    ; 读 g_Armed(0x35008)
0x63A24  je   return_0                    ; 未 armed → 拒绝
0x63A30  mov  eax, 0xFFFFFFCF / not        ; 返回 0x30
```

### 5.1 token 表

| 逻辑 k | token（载荷首 dword） | 结果 |
|---|---|---|
| 0 | `0x63AE442D` | ❌ 位 0 置位 → 拒绝 |
| 1 | `0x63AE442E` | ❌ 位 1 |
| 2 | `0x63AE442F` | ❌ 位 2 |
| **3** | **`0x63AE4430`** | ✅ |
| **4** | **`0x63AE4431`** | ✅ |
| **5** | **`0x63AE4432`** | ✅ |
| **6** | **`0x63AE4433`** | ✅ |
| **7** | **`0x63AE4434`** | ✅ |
| 8 | `0x63AE4435` | ❌ 位 8 |
| **9** | **`0x63AE4436`** | ✅ |
| **10** | **`0x63AE4437`** | ✅ |
| 11 | `0x63AE4438` | ❌ 位 11 |

即：**7 个可用命令**，掩码 `0x907` 把 `{0,1,2,8,11}` 挖掉（这几个位置很可能是已废弃/内部保留的命令，或需要另一把钥匙）。
`token(k) = (0x100000000 - 0x9C51BBD3) + k = 0x63AE442D + k`。

### 5.2 二道闸

通过 token 校验后还要看全局 `dat_35008`（`sub_2060` 就是 `mov eax,[0x35008]; ret`）：

- `dat_35008 == 0` → 放行；
- 非 0 → 返回 `0x30`（48）。

这与 `g_KillSwitch(0x35650)` 是两个独立开关：`0x35650` 卡的是**能不能进来**，`0x35008` 卡的是**进来后能不能执行**。

### 5.3 派发链（执行顺序，`sub_625B1` 内）

链的形式是 `cmp eax, token_k ; jne <下一块>`，命中即落入该命令自己的处理入口。

| 顺序 | k | token | 判定 | `cmp` 站点 | 不等跳转 | 命中入口 |
|---|---|---|---|---|---|---|
| 1 | 0 | `0x63AE442D` | reject | `0x0627AC` | — | `0x0627B3` |
| 2 | 8 | `0x63AE4435` | reject | `0x062862` | `0x0628D2` | `0x06286D` |
| 3 | 1 | `0x63AE442E` | reject | `0x0628D2` | `0x062910` | `0x0628DD` |
| 4 | **3** | **`0x63AE4430`** | **ACCEPT** | `0x062910` | `0x06294A` | `0x06291B` |
| 5 | **10** | **`0x63AE4437`** | **ACCEPT** | `0x06294A` | `0x062A60` | `0x062955` |
| 6 | 11 | `0x63AE4438` | reject | `0x062A60` | `0x062B24` | `0x062A6B` |
| 7 | **4** | **`0x63AE4431`** | **ACCEPT** | `0x062B24` | `0x062C1A` | `0x062B2F` |
| 8 | **5** | **`0x63AE4432`** | **ACCEPT** | `0x062EC5` | `0x062F64` | `0x062ED0` |
| 9 | **9** | **`0x63AE4436`** | **ACCEPT** | `0x062F64` | `0x062FA2` | `0x062F6F` |
| 10 | 2 | `0x63AE442F` | reject | `0x0637E6` | `0x063886` | `0x0637F1` |

清单另存：`out/listing/token_chain.txt`（`python tools\token_chain.py` 可重新生成）。

两个观察：

1. **被拒的 5 个 token 也在链上**（0/1/2/8/11），说明它们是"走得到、但被更外层拒绝"的历史命令——`0x907` 掩码是后来加上的封条，链本身没删。
2. **k=6 / k=7 不在链上**：全镜像搜索 `0x63AE4433` / `0x63AE4434` 命中 0 处。它们要么走默认分支，要么需要另一次握手后才被启用（推测：对应需要更高权限的命令）。

### 5.4 每个 token 到底做什么（已定稿）

把 5 个 ACCEPT 入口各追 260 条指令后，全部在 **`0x638AA` 汇流**，而汇流点是一段固定的回包构造：

```asm
0x638AA  mov   eax, r13d                 ; 默认结果（r13d = 0）
0x638AD  test  r12, r12                  ; r12 = 输出缓冲
0x638B0  je    0x63920                   ; 空指针 → 走失败分支
0x638BC  mov   dword ptr [r12],   0x01343BEB   ; ← 回包签名
0x638C4  mov   dword ptr [r12+4], 0x30         ; ← 结构长度 = 48
0x638E8  mov   dword ptr [r12+8], ebx          ; ← 结果/状态
```

**所以 `0x222824` / `0x22282C` 这条通道本质是"状态查询 RPC"**：每个 token 选定"回哪个状态"，回包恒为 48 字节 `{0x01343BEB, 0x30, status}`。

各 token 的**判定谓词**（追到的前 15 条内，均在汇流前）：

| token | 判定 | 关键指令 | 读的状态 |
|---|---|---|---|
| **k=3** | 调 `sub_7CE0`，成功则取 `r13d` | `call 0x7CE0; test eax,eax; cmovns ebx,r13d` | `dat_35C80`（注册完成标志；`0x7E05` 里置 1 / 清 0） |
| **k=4** | 取全局标志的 **bit 3** | `movzx eax,[0x35B28]; shr al,3; test al,1` | `0x35B28` 位掩码 |
| **k=5** | 取全局标志的 **bit 1** | `movzx eax,[0x35B28]; shr al,1; test al,1` | `0x35B28` 位掩码 |
| **k=9** | 比较请求体字段 + 调 `0x71E0` | `cmp [rbx+0x20],r13; setne cl; call 0x71E0` | 请求体 `+0x20` 与 0 比较 |
| **k=10** | 直接给结果码 | `mov ebx,0xFFFFFF52` / `0xFFFFFFCE` | 常量（-174 / -50） |

三点结论：

1. **token 不是"能力编号"，是"状态位选择器"** —— 5 个命令读的是同一批全局标志的不同位/不同来源。`0x35B28` 是子系统就绪位图，`0x35C80` 是注册完成标志。
2. **重活不在这里**：真正干活的路径是提交端 `0x6392E`（`sub_3000` → 事件等待 → 执行体），这条查询通道只负责回收状态。所以"k=5 = 读内存"这类猜测可以排除——7 个 token 都不会直接做内存操作。
3. **回包签名 `0x01343BEB`** 是客户端校验响应用的第一道门：伪造回包必须带上这个魔数 + 长度 0x30，否则用户态直接丢弃。

## 6. 三个控制码的语义

| 控制码 | 输入长度 | 输出要求 | 处理概要 |
|---|---|---|---|
| `0x222824` | `0x24C` | ≥ 4（深路径 ≥ `0x30`） | 解码 → token 校验 → `dat_35008` 闸 → `KeWaitForSingleObject` 等事件 → `sub_2950`(→`0x625B1`) → `KeSetEvent` → 写回 ≥ 0x30 字节 |
| `0x22282C` | `0x24C` | ≥ 4 | 同一封套的第二通道（同结构、同解码、同校验），差别在尾部动作 |
| `0x222834` | 未强制 `0x24C` | — | `ecx = ~0x222834`（归一化回自身）→ `sub_2720(...,0x78)`：提交/校验 120 字节结构 |
| `0x80000063` | METHOD_NEITHER | — | 辅助通道（用户指针直取），出现 1 次 |
| `0x80000267` | METHOD_NEITHER | — | 辅助通道（同上） |

`0x625B1` 是一个 5 KB 的保护函数，可达 `IoRegisterShutdownNotification` / `IoUnregisterShutdownNotification` / `KeBugCheckEx` / `KeInitializeGuardedMutex`——即"请求-响应"里的实际执行端。

## 9. token → 具体动作：已定稿与遗留

### 9.1 定稿部分

| 项 | 状态 |
|---|---|
| 12 个 token 的取值与公式 `0x63AE442D + k` | ✅ 由 `add 0x9C51BBD3` 反推，`tools/envelope.py` 自测通过 |
| 接受集合 `{3,4,5,6,7,9,10}`、拒绝集合 `{0,1,2,8,11}` | ✅ 掩码 `0x907` + `bt` 直接读出 |
| 派发链执行顺序、比较站点、命中入口 | ✅ `tools/token_chain.py`，见 §5.3 |
| 每条命令的**判定谓词** | ✅ 见 §5.4（5 个 ACCEPT 全部追到汇流点） |
| 回包格式 `{0x01343BEB, 0x30, status}` | ✅ `0x638BC` 三条 mov |
| 二道闸 `dat_35008` | ✅ `sub_2060` |
| 封套格式与编解码算法 | ✅ §2 / §4，可往返自测 |

**结论**：这条 RPC 通道是**状态查询**，不是"能力调用"；7 个 token 读的是不同状态位，重活在提交端 `0x6392E`。

### 9.2 遗留（明确标注）

| 遗留项 | 影响 | 补法 |
|---|---|---|
| k=6 / k=7 的分派点 | 这两个 token 通过掩码校验，却不在链上 | 追踪 `0x6392E` 的提交端是否把 token 转交执行体；或在 `0x625B1` 里找 `sub`/`xor`+`jz` 形式的隐式比较 |
| `0x35B28` 各位的写入者 | 决定每个 bit 对应哪个子系统 | 在 `.tvm0` 内搜对该地址的写（`mov [rip+disp], imm`），当前 model 只覆盖 `.text` |
| 提交端 `0x6392E` 的完整语义 | 真正干活的地方（进程/内存/物理页操作在这里） | 用 `tools/trace.py 6392e 20000` 落盘后逐块读，或按 §9.3 动态打点 |

## 10. 工具用法

```powershell
python tools\envelope.py                       # 自测：编解码往返 + 可用 token
python -c "import sys;sys.path.insert(0,'tools');from envelope import *;open('req.bin','wb').write(make_request(3, b'HELLO', key=0x11223344))"
```

生成 `req.bin`（588 字节）后，用户态可直接下发：

```c
HANDLE h = CreateFileW(L"\\\\.\\Global\\ACE-ADVT", GENERIC_READ|GENERIC_WRITE,
                       0, NULL, OPEN_EXISTING, 0, NULL);
DWORD out[12] = {0};
DeviceIoControl(h, 0x00222824, req, 0x24C, out, sizeof(out), &ret, NULL);
```

前提：`g_KillSwitch == 0` 且 `dat_35008 == 0`（否则一律 `0xC0000001` / `0x30`）。
