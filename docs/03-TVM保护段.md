# 03 · `.tvm0` 保护段分析

`.tvm0` 是 ACE（Anti-Cheat Expert）打包器插入的保护段：`0xE0000`（917,504）字节，占整个文件 78.5%，`SizeOfImage` 被扩到它的末尾。加载器把它当普通可执行段映射，真正的异常表/重定位表也搬进了它的尾部。

## 1. 段首容器头

```
0x049000  21 6D 64 62 3D 16 00 00 00 1F 00 00 00 21 73 65   !mdb=........!se
0x049010  65 64 3D C3 4B E6 69 00 00 00 00 44 65 62 75 67   ed=.K.i....Debug
0x049020  5C 41 43 45 2D 41 44 56 54 2E 73 79 73 2E 70 72   \ACE-ADVT.sys.pr
0x049030  69 76 61 74 65 5F 64 62 67 30 23 62 07 00 6B 81   ivate_dbg0#b..k.
```

| 偏移 | 内容 | 解读 |
|---|---|---|
| `+0x00` | `21 6D 64 62` = `!mdb` | 容器魔数（打包器标识） |
| `+0x04` | `3D 16 00 00` | 版本/布局字段：0x163D |
| `+0x08` | `1F 00 00 00` | 0x1F：条目/区段计数类字段 |
| `+0x0C` | `21 73 65 65 64 3D` = `!seed=` | 种子标记，后接 8 字节种子 `C3 4B E6 69 00 00 00 00` |
| `+0x18` | `Debug\ACE-ADVT.sys.private_dbg0` | **泄露的 PDB 路径**：私有调试符号名 |
| `+0x36` | `#b` 等 | 后续元数据 |

这条 PDB 路径说明该驱动是用 `private_dbg0` 配置构建的私有版本，符号未随发布件剥离（只是 PE 调试目录里的指针被清零了）。

## 2. 熵分布（4 KB 块）

| 偏移 | 熵 | 特征 | 判读 |
|---|---|---|---|
| `+0x00000`–`+0x0FFFF` | 7.31–7.40 | 前 64 KB 高熵 | 加密/压缩的元数据表、种子派生常量 |
| `+0x14000`–`+0x17FFF` | 6.04 | 明显下凹 | 表结构（大量零/小整数） |
| `+0x18000`–`+0xC7FFF` | 5.80–6.42 | 稳定在 6.0 附近 | **原生 x86-64 代码**（典型代码熵 5.9–6.2） |
| `+0xC8000`–`+0xD3FFF` | 7.12–7.28 | 再次高熵 | 另一块加密表 / 常量池 |
| `+0xD8000`–`+0xDBFFF` | 6.72 | 中高 | 混合 |
| `+0xDC000`–`+0xDFFFF` | 4.10 | 接近结构化数据 | 段尾表（重定位/异常/字符串指针） |

注意 `+0x18000` 之后能看到干净的指令序列：

```
0x04A800  24 E0 FC FF            and al, 0FCH
0x04A803  48 8D A4 24 88 FD FF FF   lea rsp, [rsp - 0x278]
0x04A80B  48 89 6C 24 08         mov [rsp + 8], rbp
```

以及大量"跳板"型混淆：

```
0x04B000  49 81 C0 32 E4 44 3C   add r8, 0x3C44E432
          9D 41 FF E0            jmp r8                  ; 绝对间接跳转，静态不可跟
```

`jmp r8` 前紧跟 `add r8, imm32`，是典型的**动态地址合成**：真实目标 = 编译期常数 + 运行时基址修正，静态分析无法直接解出跳转图。

## 3. 段尾三张表

| RVA | 大小 | 内容 |
|---|---|---|
| `0x123000` | `0x0F70` | 基址重定位表，**184 个块**（每块 `pageRVA + blockSize + N×2 字节项`） |
| `0x124000` | `0x3228` | 异常表，**1,070 条** RUNTIME_FUNCTION |
| `0x129000` | — | `SizeOfImage` 终点 |

第一块样例：`00F00200 10000000 A0A2 A8A2 B8A2 0000` → page RVA `0x2F000`（`.rdata` 起点），块大小 `0x10`，4 个重定位项，其中一项为 `0x0000`（块终止符）。这与 `.rdata` 起点的 IAT 表头位置吻合——说明重定位表覆盖的是**被搬移过的原始镜像**。

异常表的头部几条：

```
begin=0x001010 end=0x00102D unwind=0x030D88
begin=0x00102D end=0x001641 unwind=0x030D90
begin=0x001641 end=0x00164C unwind=0x030DC0
begin=0x001650 end=0x001679 unwind=0x030DE4
```

与 `.pdata` 段副本的前几条逐字节相同，但总数少 76 条 `.text` 记录、多 111 条 `.tvm0` 记录。**结论**：打包器重写异常目录时，用"当前镜像实际包含的函数集合"重建了这张表，`0x124000` 是权威版本。

## 4. 运行时会发生什么（推断链）

证据链：

1. `DllCharacteristics` 含 `FORCE_INTEGRITY`，加载前会校验签名；
2. `INIT` 段只有 0xACA 字节，但 `DriverEntry` 立刻 `call sub_1da0`，进入 `.text` 主流程；
3. 目录 3/5 指向 `.tvm0`，且段特征为 `code|exec|read`（`0x68000020`），映射后可直接执行；
4. 段首有容器头（魔数 + 种子 + 计数），前 64 KB 高熵；
5. 111 个 `.tvm0` 函数被登记进异常表 → 它们的栈帧需要 unwind 信息 → 它们会被**真实调用**，不是纯数据。

因此合理推断：`.tvm0` = 打包器塞进来的第二镜像区，`INIT`/`.text` 的引导代码用 `!seed` 派生的密钥解开容器头指向的表项，把受保护代码就地映射/解密后调用；`0x123000`/`0x124000` 两张表随之生效，让加载器能正确处理这些函数的异常展开。

## 5. 对重建工作的影响

**零影响**，因为本工程走"字节保真"路线：

- `.tvm0` 整段按 `db` 转录（`src/masm/ace_advt.asm` 中 57,344 行数据），不做语义解释；
- 段尾三张表同样是数据，一并转录；
- 111 个函数的边界只用于标签命名，不参与编码。

也就是说：即使 `.tvm0` 的内部格式完全未知，重建产物仍然逐字节相同。若后续要真正逆向 TVM 字节码，需要先解出容器头（`!seed` 之后的结构），这属于独立的第二阶段工作。

## 6. 值得注意的字符串与 API 组合

| 现象 | 数量 | 含义 |
|---|---|---|
| `.rdata` 可打印字符串 | 34 条 | 几乎全部常量已下沉/加密 |
| `MmGetSystemRoutineAddress` 调用点 | 78 | 运行时解析内核例程，规避导入表静态特征 |
| `KeBugCheckEx` 调用点 | 31 | 完整性校验失败的处置路径 |
| `MmGetPhysicalAddress` / `MmAllocateContiguousMemory` | 16 / 8 | 物理内存访问能力 |
| `PsLookupProcessByProcessId` + `KeStackAttachProcess` | 9 + 8 | 跨进程内存读写 |
| `IoRegisterShutdownNotification`、`KeRegisterBugCheckReasonCallback` | 有 | 关机/蓝屏回调挂钩 |

这套 API 组合与"反作弊驱动的内存扫描 + 进程保护"职责一致。
