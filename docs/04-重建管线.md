# 04 · 重建管线与工具链

目标：从反汇编文本出发，用商业级汇编器重新生成一个**逐字节相同**的 PE 镜像。这比"生成等价二进制"要求高得多——每一条指令的**编码形式**（不是语义）都必须与 MSVC 当年选的完全一致。

## 1. 总体流程

```
reference ACE-ADVT.sys
        │
        ├─(1) tools/analyze.py ──► out/model.json         43,363 个字节单元 + 标签
        │                              │
        ├─(2) tools/emit_masm.py ──────┴──► src/masm/ace_advt.asm    42k 指令 + 60k 数据行
        │                                       │
        ├─(3) ml64 /c ─────────────────────────┴──► build/ace_advt.obj
        │                                       │
        ├─(4) tools/coff.py                     │  读取 COFF：段数据 + 符号表 + 1,950 条 REL32
        │       + 平铺 RVA 空间拼装 ◄───────────┘
        │
        ├─(5) tools/mkheaders.py ──► out/assets/headers.bin   字段级重建，1024 字节零差异
        │
        └─(6) 切片 + 打包 ──► out/rebuild/ACE-ADVT.rebuilt.sys
                  ▲
                  └── src/asm/assets/authenticode.asm（21,168 字节签名，db 转录）
```

## 2. 为什么用平铺 RVA 空间

原文件的 RVA 与文件偏移**不是**固定差值：

```
.text   va=0x001000  raw=0x000400   Δ=0xC00
.rdata  va=0x02F000  raw=0x02DE00   Δ=0xC00
.data   va=0x035000  raw=0x033800   Δ=0xC00
.pdata  va=0x042000  raw=0x033C00   Δ=0x6000   ← 断了
```

原因是 `.data` 的 `VirtualSize`（0xC402）远大于 `RawSize`（0x400），中间的 BSS 尾部不占文件空间。所以不能用一个 `org` 让汇编输出直接等于文件内容。

解决办法：**在一个连续的 RVA 空间里汇编**，从 `org 0x1000` 一直到 `0x129000`，段与段之间的虚拟空洞用 `db N dup(0)` 填。这样：

- 所有标签地址 = `image_base + rva`，RIP 相对引用与分支目标自动算对；
- 汇编产物长度 0x128000 = `SizeOfImage - 0x1000`；
- 打包阶段再按"每段的 raw 偏移"切片，把 BSS 空洞丢掉，得到 0x118000 字节的 body。

## 3. 为什么主力用 ml64 而不是 NASM

同一段汇编，两个汇编器选的编码不同：

| 源码 | MSVC 原始字节 | ml64 | NASM |
|---|---|---|---|
| `mov rcx, rbx` | `48 8B CB`（`MOV r64, r/m64`） | `48 8B CB` | `48 89 D9`（`MOV r/m64, r64`） |
| `xor ecx, ecx` | `33 C9` | `33 C9` | `31 C9` |
| `add rcx, rbx` | `48 03 CB` | `48 03 CB` | `48 01 D9` |
| `cmp rbx, rcx` | `48 3B D9` | `48 3B D9` | `48 39 CB` |
| `or eax, ebx` | `0B C3` | `0B C3` | `09 D8` |

寄存器→寄存器形式的双操作数指令有两个等长编码，MSVC 与 ml64 都选 `r, r/m` 方向，NASM 选 `r/m, r` 方向。实测影响面：

| 工具链 | 助记符直接汇编成功 | 需按原始字节回落 |
|---|---|---|
| NASM | 31,034 / 42,528（72.97%） | 11,494 条 |
| **ml64** | **41,934 / 42,528（98.60%）** | **594 条** |

这就是把主力工具链换成微软原厂汇编器的直接理由：**不是"更正统"，而是省掉 1 万处不必要的字节补丁**。

## 4. 迷你链接器（`tools/coff.py`）

ml64 不生成可执行文件，只出 COFF 目标文件。因为整个镜像是一个 `FLAT` 段，所有跨段引用都变成了同段内引用，但 MASM 仍然会为 RIP 相对引用生成重定位项（`IMAGE_REL_AMD64_REL32`），并在指令里留 `disp = 0`。

回填规则（单段平铺，段基址为 0）：

```
target = section_base + symbol.value = 0 + symbol.value
REL32          →  disp = target - (reloc_rva + 4)
REL32_1..REL32_5 →  disp = target - (reloc_rva + 4 + n)
ADDR64/ADDR32  →  直接写 target
```

因为只差一个偏移量，段最终落在哪个 RVA 都不影响结果——这也是平铺技巧能成立的根本原因。

实测：**1,950 条重定位**全部为本模块符号，无外部引用，回填后 `flat` 长度 0x128000，与原镜像的 RVA 空间完全对齐。

## 5. 头部与签名的处理

| 部件 | 处理方式 | 校验 |
|---|---|---|
| DOS 头（0x40） | 14 个字段 `struct.pack` 重建 | 与原件一致 |
| DOS stub + Rich 头（0xB0） | `src/asm/assets/dos_stub.asm` 的 `db` 转录 → `ml64`？否，直接 `nasm -f bin` 组装 | 组装结果与原件一致 |
| PE/COFF/可选头/目录/段表（0x338） | `tools/mkheaders.py` 逐字段写入 | 824 字节零差异 |
| 头部填充到 0x400 | 补零 | 与原件一致 |
| Authenticode（0x52B0） | `src/asm/assets/authenticode.asm` 转录，构建后追加 | 转录前后一字节不差 |

签名块是**唯一无法从结构推出来的输入**（它是微软签名服务器的输出），所以作为构建资产存在于源码树里，而不是"免检"的二进制文件。同理 Rich 头（编译器版本向量 + XOR 密钥）也是工具链指纹，属于资产。

## 6. 差异收敛循环（settle loop）

第一次汇编不可能 100% 命中，原因是少数指令存在"等价但编码不同"的情况（见 docs/05 的分类表）。`build_masm.py` 用三步闭环把差异压到 0：

| 步骤 | 检测手段 | 动作 |
|---|---|---|
| 长度缺陷 | 相邻两行在 MASM listing 里的**输出偏移差** ≠ 该指令应有的长度（偏移差与整体位移无关，因此一轮即可全部发现） | 该行降级为 `db <原始字节>` |
| 编码缺陷 | 每行在其实际输出偏移处的字节 ≠ 原始字节 | 该行降级为 `db` |
| 语法缺陷 | `ml64` 报错（行号 → `line_map.json` → RVA） | 该行降级为 `db` |

降级表落在 `out/emit_overrides.json`，下一轮重新生成源码时该行直接写成 `db`，**偏移保持不变**，因此循环单调收敛。

实际收敛过程：

| 轮次 | 助记符行 | 回落 | 结果 |
|---|---|---|---|
| 1 | 42,493 | 35 | ml64 报 34 个语法/操作数错误 → 降级 |
| 2 | 42,459 | 69 | 484 个长度缺陷（`push imm8` vs `push imm32` 等）→ 降级 |
| 3 | 41,975 | 553 | 41 处同长异码 → 降级 |
| 4 | 41,934 | 594 | **0 差异，字节全同** |

`-Fresh` 会清空降级表从头跑，四轮后得到同一个哈希——这一点在 docs/05 有复现记录。

## 7. 产物确定性与复现性

| 因素 | 处理 |
|---|---|
| 时间戳 | 取自原头 `0x69E74BB4`，非构建时间 |
| 校验和 | 用标准算法对最终字节重算，等于原值 `0x124E80`（不相等则强行改为原值并报警） |
| 汇编器版本 | 记录在 `out/verification.json`（ml64 14.52.36815） |
| 随机性 | 全流程无随机源；`db` 数据来自模型，不来自"当前文件" |
| 段顺序 | 固定按 RVA 排序，平铺空间 + 虚拟空洞 |

## 8. NASM 备用路径

`tools/emit_asm.py` + `tools/build.py` 提供同一模型的 NASM 版本，产物哈希相同（那也是第一次成功一致的工具链）。保留它的价值：

- 交叉验证：两套汇编器独立收敛到同一字节流，说明模型（分区与指令边界）本身正确；
- NASM 的 listing 更易读（`;@rva` 标记 + 原始字节列）；
- 无 VS 环境的机器上也能构建。

`.\build.ps1 -Nasm` 可切换。

## 9. 第二套汇编器交叉验证（EWDK 25H2）

挂载的 **EWDK**（`F:`，`br_release_svc_im.28000.2526`）自带另一套独立的微软工具链：VS Build Tools 18 / MSVC `14.50.35717` / `ml64 14.50.35724`，以及 WDK `10.0.28000.0` 的 `km` 头与 82 个 `x64` 库（`wdm.lib`、`ntoskrnl.lib`、`BufferOverflowK.lib` 等）。

`tools/build_masm.py` 的汇编器路径支持 `%ML64%` 覆盖，因此同一份源码可以在两套版本上分别汇编：

```powershell
$env:ML64='F:\Program Files\Microsoft Visual Studio\18\BuildTools\VC\Tools\MSVC\14.50.35717\bin\Hostx64\x64\ml64.exe'
python tools\build_masm.py
```

结果：

| 汇编器 | 版本 | 助记符行 | 回落 | 字节差异 | SHA256 |
|---|---|---|---|---|---|
| E:\…\14.52.36815\ml64.exe | 14.52.36815 | 41,934 | 594 | 0 | `4C14…3FF8` |
| F:\…\14.50.35717\ml64.exe (EWDK) | 14.50.35724 | 41,934 | 594 | 0 | `4C14…3FF8` |

**两套汇编器版本产出同一字节流，且用的是同一张降级表（没有新增回落）**。这说明编码选择在这些指令族上是跨版本稳定的，也排除了"只有某个特定汇编器版本才能复现"的偶然性。

> 顺带记录一个能力边界：原文件的可选头写着 **linker version 14.28**（VS 2019 16.11 一代），而两台机器上最近的是 14.29。即便将来把逻辑重写成 C，也不可能靠"换回同版本编译器"复现字节——编译器版本、寄存器分配、内联决策都无法回溯。字节保真的唯一可靠路径是本文这条"重汇编"路线。
