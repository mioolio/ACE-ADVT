# 06 · 功能分析：这个驱动到底在干什么

## 0. 一句话结论

`ACE-ADVT.sys` 是 **腾讯 ACE（Anti-Cheat Expert）反作弊体系的 x64 内核过滤器驱动**，设备名 `\Device\ACE-ADVT`，对外只暴露 3 个控制码 + 一个"信封格式"的 RPC 通道；真正的业务逻辑（进程/内存/线程操作、完整性检查、反调试）**全部被搬进 `.tvm0` 保护段**，用一个控制流平坦化器 + 动态 API 解析 + 加密字符串表保护起来。`.text` 里留下的只是一个骨架：初始化、设备创建、单实例门禁、引用计数、卸载、以及一大批"给保护段调用的能力函数"。

| 维度 | 事实（证据） |
|---|---|
| 产品 | ACE 反作弊驱动（`ACE-ADVT.sys`，同目录 `ACE-BASE.sys` / `ACE-BOOT.sys` / `ACE-CORE*.sys` / `SGuard64.exe`） |
| 设备 | `\Device\ACE-ADVT` ↔ `\DosDevices\Global\ACE-ADVT`（`sub_1da0`，字符串 @ `0x2F338` / `0x2F300`） |
| 设备类型 | `FILE_DEVICE_UNKNOWN (0x22)`，`IoCreateDevice` 调用点 `0x1F0E` |
| 入口 | `INIT:0x46000` → `sub_1da0`（设备/符号链接/派发表）→ `sub_17c0`（子系统注册） |
| 派发表 | CREATE=`sub_1680`，CLOSE=`sub_1650`，DEVICE_CONTROL=`sub_1700`，SHUTDOWN=`sub_1d70`，Unload=`sub_1c30` |
| 保护段 | `.tvm0` 917,504 字节，975 处计算型跳转，111 个异常记录登记的函数 |
| 字符串 | `.rdata` 仅 34 条可打印串，API 名/设备名之外的常量全部加密存放（`0x2F3B0` 起的高熵区） |
| 签名 | WHCP 签名（`FORCE_INTEGRITY` 置位，加载前校验） |

## 1. 生命周期

```
DriverEntry (0x46000)
 ├─ sub_4602c          CFG/安全 cookie 初始化
 └─ sub_1da0           主初始化
     ├─ 填 MajorFunction[IRP_MJ_CREATE]        = sub_1680
     │   MajorFunction[IRP_MJ_CLOSE]           = sub_1650
     │   MajorFunction[IRP_MJ_DEVICE_CONTROL]  = sub_1700
     │   MajorFunction[IRP_MJ_SHUTDOWN]        = sub_1d70
     │   DriverObject->DriverUnload            = sub_1c30
     ├─ RtlInitUnicodeString(&g_devname,  "\Device\ACE-ADVT")
     ├─ RtlInitUnicodeString(&g_symlink,  "\DosDevices\Global\ACE-ADVT")
     ├─ UnicodeString → AnsiString 转码（两份副本 @ 0x35370 / 0x353F0，疑似给后续比对/日志用）
     ├─ IoCreateDevice(DriverObject, 0, &devname, 0x22, FALSE, &g_DeviceObject)
     ├─ IoCreateSymbolicLink(&symlink, &devname)
     ├─ sub_17c0           子系统注册（回调/线程/定时器）
     ├─ g_DriverObject = DriverObject (0x35350)
     └─ g_DeviceObject = DeviceObject (0x35358)
```

失败路径完整：`IoCreateSymbolicLink` 失败 → `IoDeleteSymbolicLink`；`IoCreateDevice` 失败 → 直接返回，**不留下半初始化状态**。

## 2. 访问控制：单实例 + 全局门禁

### 2.1 CREATE (`sub_1680`, 115 字节)

```asm
KeAcquireGuardedMutex(&g_Mutex)        ; g_Mutex = 0x35660
call loc_2090                          ; → gate
test al, al
je   reject                            ; al==0 → 拒绝
lock inc [g_OpenCount]                 ; 0x35348
mov  [g_InFlight], 0                   ; 0x3534C
KeReleaseGuardedMutex(&g_Mutex)
...
reject:
mov ebx, 0C0000425h                    ; STATUS_xxx（拒绝）
```

### 2.2 门禁 `loc_2090`（3 条指令）

```asm
00002090  cmp qword ptr [g_KillSwitch], 0     ; 0x35650
00002098  sete al
0000209b  ret
```

**这是全驱动的总开关**：`g_KillSwitch == NULL` 才放行。任何把 `0x35650` 写成非零的路径，都会让 CREATE 与 DEVICE_CONTROL **全部**立刻失败。这个全局量是后续绕过分析的核心锚点。

### 2.3 CLOSE (`sub_1650`)

`lock dec [g_OpenCount]`，清零设备扩展字段，`IofCompleteRequest`。也就是说设备句柄是**引用计数**语义，允许多次打开、逐个关闭。

> 结论：接口是"**单客户端 RPC 通道**"——一个用户态组件（`ACE-Service64.exe` / `SGuard64.exe`）持有一个长期句柄，所有命令都走这**一条**通道。

## 3. IOCTL 接口面

`IRP_MJ_DEVICE_CONTROL` → `sub_1700` → `jmp 0x6CF71`（`.tvm0` 内，613 字节，混淆）。

### 3.1 入口现场（从混淆中还原）

| 步骤 | 指令 | 含义 |
|---|---|---|
| 1 | `mov rax, [rdx+0xB8]` | `Irp->Tail.Overlay.CurrentStackLocation` |
| 2 | `mov r14, [Irp+0x18]` | `Irp->AssociatedIrp.SystemBuffer` |
| 3 | `mov esi, [Iosl+0x08]` | `OutputBufferLength` |
| 4 | `mov r15d,[Iosl+0x10]` | `InputBufferLength` |
| 5 | `mov ebx, [Iosl+0x18]` | `IoControlCode` → 存 `g_LastIoctl`(`0x35330`) |
| 6 | `call loc_2090` | 同一个门禁 |
| 7 | `lock xadd [g_InFlight], 1` | 在飞请求计数 |
| 8 | `call sub_2480` → `0x61DC6` | 真正的派发器（也在 `.tvm0`） |

### 3.2 控制码（静态提取的全部 5 个常量）

| 控制码 | DeviceType | Function | Method | Access | 出现次数 |
|---|---|---|---|---|---|
| `0x00222824` | `0x22` | `0xA09` | BUFFERED | ANY | 2 |
| `0x0022282C` | `0x22` | `0xA0B` | BUFFERED | ANY | 2 |
| `0x00222834` | `0x22` | `0xA0D` | BUFFERED | ANY | 2 |
| `0x80000063` | `0x8000` | `0x018` | NEITHER | ANY | 1 |
| `0x80000267` | `0x8000` | `0x099` | NEITHER | ANY | 1 |

三个 `0x22/0xA09..0xA0D` 是**主通道**（BUFFERED，`SystemBuffer` 双向），两个 `0x8000` 是辅助通道（METHOD_NEITHER，直接拿用户指针）。注意 `Function` 字段的取值 0xA0x 明显不是顺序编号——说明控制码是**产品自定义编号**，且 0xA09/0xA0B/0xA0D 之间跳号（0xA0A / 0xA0C 被保留或已废弃）。

### 3.3 信封格式（`0x222824` 分支实测）

```
输入缓冲 (SystemBuffer)
+0x00  DWORD  magic / version     必须 == 0x24C        ← cmp dword [rsp+0x280], 0x24C
+0x04  ...    (其余字段由解析器填充)
+0x24  DWORD  length               必须 <= 0x200        ← mov edx,[rbx+0x24]; cmp edx,0x200
输出缓冲
+0x00  DWORD  status               要求 OutputBufferLength >= 4
```

处理流程（还原后）：

```c
if (Request->magic != 0x24C)            return STATUS_INVALID_PARAMETER;   // → 0x6246E
memset(&local, 0, 0x200);               // sub_2E780 = memset
rbx = translate_request(Request);       // 输入 → 内部 0x200 结构
if (!rbx)                               return STATUS_...;                  // → 0x6214B
if (Request->length > 0x200) {          // 超长直接拒
    status = ~3;                        // 0xFFFFFFFC
    goto write_status;
}
...
write_status:
if (OutputBufferLength < 4)             return STATUS_BUFFER_TOO_SMALL;    // → 0x6246E
*(DWORD*)SystemBuffer = status;
```

`sub_2E780` 是 `memset`（按 8 字节展开 + SSE），`sub_2E440` 是 `memmove`（两函数被 58 / 39 个函数复用，属于 CRT 内联副本）。

> 也就是说：三个主控制码共用同一个"信封 + 内部操作码"的协议，**真正的命令编号藏在请求结构里**（`[rbx+0x24]` 之后的分支），而不是 IOCTL 码本身。这与 ACE 一贯的"单通道 RPC"设计一致：外部看不到命令清单，只有拿到内部协议才能枚举能力。

## 4. `.tvm0` 保护段解剖

### 4.1 容器头

```
0x049000  21 6D 64 62 3D 16 00 00 00 1F 00 00 00 21 73 65 65 64 3D ...
          "!mdb"      ver=0x163D  count=0x1F  "!seed=" <8 字节种子>
0x049018  "Debug\ACE-ADVT.sys.private_dbg0"     ← 泄露的 PDB 路径
```

### 4.2 控制流平坦化（975 处）

每个基本块之间不是普通跳转，而是：

```asm
movabs rcx, 0x194F5E764     ; 高位常数
pushfq
add    rcx, -0x54EF17AD     ; + 低位常数（负偏移）
popfq
jmp    rcx                  ; 目标 = 两常数之和
```

中间夹着 `xchg r10, rax` / `not rax` / `lea` 伪装的垃圾指令，以及跳到镜像外的诱饵 `jmp`。**常量折叠后 975 处全部可解析**（本工程的 `tools/trace.py` 就是干这个的），真实目标地址全部落在 `0x5D000..0x83000` 区间。

### 4.3 111 个受保护函数（异常表登记）

按"能到达的 .text 能力函数 → 其导入 API"归类：

| 主类别 | 函数数 | 代表 | 可达 API |
|---|---|---|---|
| 进程 | 8 | `0x63C29`(28.6 KB) | `PsLookupProcessByProcessId`、`KeStackAttachProcess`、`IoGetCurrentProcess`、`ZwOpenProcess`、`ZwQueryInformationProcess`、`ExGetPreviousMode` |
| 崩溃回调 | 5 | `0x625B1`(5.0 KB) | `KeRegisterBugCheckReasonCallback`、`KeBugCheckEx` |
| 注册表 | 1 | — | `ZwOpenKey`、`ZwDeleteValueKey`、`RtlGetVersion` |
| 池 | 1 | — | `ExAllocatePoolWithTag`、`ExFreePoolWithTag` |
| 同步 | 1 | — | `KeAcquireGuardedMutex`、`KeInitializeGuardedMutex` |
| 直接导入（保护段内） | — | 78 处 | `PsGetCurrentProcessId` ×29、`KeBugCheckEx` ×6、`IofCompleteRequest` ×2、`IoCreateNotificationEvent`、`KeClearEvent` … |

`PsGetCurrentProcessId` 在保护段内被引用 **29 次**——每一次请求都要确认"是哪个进程在问"，这是 ACE 的调用方鉴权核心。

### 4.4 未解部分（老实交代）

| 项 | 状态 |
|---|---|
| 内部操作码表（信封里的命令编号） | 未枚举：需要完整执行 0x200 结构的解析路径（`sub_2E780` 之后的字段分支） |
| 加密字符串表（`0x2F3B0` 起） | 未解密：需要找到密钥派生点（疑似与 `!seed` 相关） |
| `.tvm0` 头 `!mdb` 之后的表项语义 | 仅有结构描述，无语义 |
| 637 KB 的"合成函数"（`0x76223`，无 unwind） | 未逐块分析：该区域是平坦化后的主体，需按 975 条边重建 CFG |

## 6. 反分析设计（这对绕过很关键）

| 设计 | 证据 | 效果 |
|---|---|---|
| 控制流平坦化 | 975 处 `movabs/add/jmp` | 静态 CFG 不可直读 |
| 诱饵分支 | 跳到镜像外的 `jmp`/`call` | 反汇编器错位 |
| 语义无操作 | `xchg r10,rax` / `not` 序列 | 干扰数据流分析 |
| 动态 API 解析 | `MmGetSystemRoutineAddress` ×78，导入表只有 82 项 | 导入表看不出真实行为 |
| 字符串加密 | `.rdata` 明文串仅 34 条 | 无法 grep 出设备名/注册表路径/API 名 |
| 自卸载 | `sub_165F0` 用 `ZwUnloadDriver` | 证据可在检测后被抹掉 |
| 单实例门禁 | `g_Mutex` + `g_OpenCount` + `g_KillSwitch` | 第三方无法插话；可一键自废 |
| 签名 + `FORCE_INTEGRITY` | 可选头 `0x1E0` | 任何磁盘改动都会被加载器拒绝 |
| 异常表搬迁 | 目录 3/5 指向 `.tvm0` | 工具按 `.pdata` 解析会漏掉 111 个函数 |
