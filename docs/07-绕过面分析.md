# 07 · 绕过面分析

> 本文按"驱动已经/尚未加载"两个阶段组织，每条给出**目标、机制、所需权限、可检测性**。
> 所有偏移都可以在本工程的 `out/model.json`、`out/graph.json`、`out/listing/ACE-ADVT.txt` 里对上原文。

## 0. 先把目标说清楚

"绕过 ACE-ADVT"在工程上可以拆成三个互不相同的目标，混在一起谈会自欺欺人：

| 目标 | 判据 | 难度 | 主要障碍 |
|---|---|---|---|
| **A. 让它不工作**（拒绝服务/自废） | 设备打不开、IOCTL 全返回错 | 低 | 无（它自己提供开关） |
| **B. 让它看不见我**（隐蔽对抗） | 它的扫描/枚举拿不到目标对象 | 高 | 进程/线程/内存三条链路都要处理 |
| **C. 让它说谎**（欺骗回传） | 它把伪造结果报给用户态 | 很高 | 单实例通道 + 调用方 PID 校验 |

下面按这个分层给手段。

---

## 1. 阶段一：加载前（最省成本）

### 1.1 名称抢占：让 `IoCreateDevice` 失败

`sub_1da0` 在 `0x1F0E` 调 `IoCreateDevice(..., L"\\Device\\ACE-ADVT", 0x22, ...)`；若该名字已存在，返回 `STATUS_OBJECT_NAME_COLLISION`，`sub_1da0` 直接走失败分支（不注册任何子系统），`DriverEntry` 返回错误 → 驱动**加载失败但不蓝屏**。

```c
// 早于 ACE 加载的驱动（boot-start 或 EarlyLaunch AM 驱动）
UNICODE_STRING name; RtlInitUnicodeString(&name, L"\\Device\\ACE-ADVT");
PDEVICE_OBJECT dev;
IoCreateDevice(MyDriver, 0, &name, FILE_DEVICE_UNKNOWN, 0, FALSE, &dev);   // 占位
```

| 项 | 值 |
|---|---|
| 需要 | 更早的加载顺序（服务 `Start` 类型 / ELAM） |
| 副作用 | ACE 侧会记录 `STATUS_OBJECT_NAME_COLLISION`，用户态可能上报异常；`ACE-BASE` 可能补装 |
| 可检测性 | 高（ACE 多处会校验设备是否由自己创建） |

变体：抢占符号链接 `\DosDevices\Global\ACE-ADVT`（`IoCreateSymbolicLink` 同样会失败，`sub_1da0` 会回滚设备）。

### 1.2 阻断加载链

ACE 的加载由 `ACE-BOOT.sys` / `ACE-BASE.sys` + 服务完成。在服务层禁用（`sc config ... start= disabled` + 删除 `ImagePath`）是最"干净"的做法，但它属于用户态对抗，ACE 的服务有自保护与重装逻辑（`ACE-Service64.exe` 会周期性重建）。

### 1.3 抢单实例句柄（温和的"占坑"）

设备是单客户端语义（`sub_1680` 的 `g_OpenCount` + `g_Mutex`）。提前 `CreateFile("\\.\Global\ACE-ADVT")` 只是**加引用计数**，不会阻止后续打开（同一进程或不同进程都能拿到句柄，只有 `g_KillSwitch` 会拒绝）。

> 所以"占坑"无效——这条要记下来：ACE 的 CREATE 不做独占检查，只做门禁检查。

## 2. 阶段二：加载后（内核态操作）

### 2.1 拉总闸：`g_KillSwitch`（`0x35650`）

```asm
0x2090: cmp qword ptr [rip+0x335b8], 0      ; g_KillSwitch
0x2098: sete al
0x209b: ret
```

任何非零值都会让 **CREATE 与 DEVICE_CONTROL 同时失败**（`sub_1680` → `0xC0000425`；`sub_1700` → `0x6D0C9` 错误分支）。

```c
// 需要任意内核写能力（自带驱动 / 已有 BYOVD / 内核调试器）
*(ULONG64*)((PUCHAR)ImageBase + 0x35650) = 1;
```

| 项 | 值 |
|---|---|
| 效果 | 驱动仍在内存，但接口全哑；用户态 `ACE-Service` 会连续失败并可能触发修复流程 |
| 可检测性 | 中：驱动自身不会再校验该字段（读-用之间无二次确认），但用户态会看到成片错误 |
| 风险 | 若 ACE 用户态有"接口失效 → 重启服务/重装驱动"逻辑，会在几十秒内被覆盖 |

### 2.2 通讯层：过滤/拦截 IOCTL

在 `\Device\ACE-ADVT` 之上挂一个过滤驱动（`IoAttachDeviceToDeviceStack`），对 `IRP_MJ_DEVICE_CONTROL` 直接 `IoCompleteRequest` 返回伪造结果：

```c
switch (stack->Parameters.DeviceIoControl.IoControlCode) {
case 0x00222824: case 0x0022282C: case 0x00222834:
    // 伪造 4 字节状态字，或原样转发但不让下层看到真实 IRP
    *(ULONG*)irp->AssociatedIrp.SystemBuffer = FAKE_STATUS;
    irp->IoStatus.Information = 4;
    irp->IoStatus.Status = STATUS_SUCCESS;
    IoCompleteRequest(irp, IO_NO_INCREMENT);
    return STATUS_SUCCESS;
}
```

这是目标 **C（让它说谎）** 的最短路径。但注意三点：

1. **被过滤的设备对象必须能被找到**：ACE 用 `IoCreateDevice` 创建后并无 `DO_BUFFERED_IO` 之外的加固，`IoEnumerateDeviceObjectList` 可枚举，也可以按名字 `IoGetDeviceObjectPointer(L"\\Device\\ACE-ADVT")` 拿到。
2. **`g_LastIoctl`（`0x35330`）** 会记录最后控制码，ACE 可能回传它做一致性校验；伪造时要同步写。
3. **`g_InFlight`（`0x3534C`）** 是原子计数器，绕过派发不会自增，若 ACE 检查"请求序号连续性"会露。

#### 2.2.1 伪造回包必须带签名（新）

`0x222824` / `0x22282C` 的回包是固定 48 字节结构，首字段是魔数（`docs/08` §5.4）：

```c
out[0] = 0x01343BEB;     // 签名，客户端第一道校验
out[1] = 0x30;           // 结构长度
out[2] = status;         // 状态/结果
```

所以过滤驱动只要**照抄这个头**、按被截获的 token 回填 `status`，用户态就会当成正常响应。因为该通道是**状态查询**（不是能力调用），伪造不涉及任何副作用，风险远低于伪造内存操作结果——这是目前性价比最高的"让它说谎"路径。

要伪造得"合理"，还得让 `status` 与被查询的状态位一致：

| token | 客户端期望的来源 | 伪造建议 |
|---|---|---|
| `0x63AE4430` (k=3) | `sub_7CE0` 读 `dat_35C80`（注册完成） | 返回 0 = "已注册" |
| `0x63AE4431` (k=4) | `0x35B28` bit 3 | 返回 0 / 置位值 |
| `0x63AE4432` (k=5) | `0x35B28` bit 1 | 同上 |
| `0x63AE4436` (k=9) | 请求体 `+0x20` 与 0 比较 | 依请求回声 |
| `0x63AE4437` (k=10) | 常量 `0xFFFFFF52` / `0xFFFFFFCE` | 原样回这两个值之一 |


### 2.3 回调面：摘掉它的取证钩子

| 钩子 | 注册点 | 摘除方式 |
|---|---|---|
| 蓝屏回调 | `sub_6E30` → `KeRegisterBugCheckReasonCallback` | 遍历 `KeBugCheckReasonCallbackListHead`，摘除 `KBUGCHECK_REASON_CALLBACK_RECORD` 并调用 `KeDeregisterBugCheckReasonCallback` |
| 关机通知 | `sub_1D20` → `IoRegisterShutdownNotification` | 对设备对象 `IoUnregisterShutdownNotification` |
| 通知事件 | `IoCreateNotificationEvent`（`.tvm0` 内 1 处） | `ZwOpenEvent` + `KeSetEvent` 主动触发，扰乱其状态机 |
| 全局回调 | `sub_7D15` → `ExCreateCallback`/`ExRegisterCallback` | `ExUnregisterCallback` |

> `KeBugCheckReasonCallbackListHead` 在 `nt!` 里是导出符号（`ntoskrnl.exe` 的 `KeBugCheckReasonCallbackListHead`），可 `MmGetSystemRoutineAddress` 解析后直接操作。

### 2.4 针对"进程看不见"（目标 B）

ACE 的进程链路是 `PsLookupProcessByProcessId` → `KeStackAttachProcess` → 内存扫描，加上 `PsGetCurrentProcessId` 侧的调用方鉴权。要让它"看不见"，得同时处理：

| 环节 | 手法 | 代价/风险 |
|---|---|---|
| 进程枚举 | 从 `EPROCESS.ActiveProcessLinks` 摘链（双向链表自环） | 系统稳定性风险；`PsGetNextProcess` 遍历不到的进程也无法被任务管理器看到 |
| PEB 信息 | 清 `PEB->ImagePathName` / `CommandLine` / `ProcessParameters` | 影响自身功能，需保留内部副本 |
| 线程枚举 | 摘 `ETHREAD.ThreadListEntry`（`PsGetNextProcessThread` 链） | 线程调度不受影响，但 `PsLookupThreadByThreadId` 仍可命中 |
| 内存扫描 | 目标代码/数据页放在 `VTL1`（HVCI/Secure Kernel）或 `MmAllocateContiguousMemory` 的物理页里，用 `MmMapIoSpace` 自映射 | 需要虚拟化支持；ACE 也会读物理内存 |
| 句柄鉴权 | ACE 用 `ExGetPreviousMode` + `ObReferenceObjectByHandle` 校验调用方，只对"自己人"放行 | 绕过它需要伪造调用进程身份（比想象中难，因为有 PID 侧校验） |
| 物理内存 | ACE 有 `MmGetPhysicalAddress` + `MmMapIoSpace` 路径 | 目标数据必须不出现在可枚举的物理页（例如放在设备 DMA 缓冲/固件保留区） |

> 关键判断：**单点隐藏无效**。`PsGetCurrentProcessId` ×29 说明它每次请求都重新确认调用方；`0x63C29`（28.6 KB 的进程处理函数）里同时有 `PsLookupProcessByProcessId` / `KeStackAttachProcess` / `ExAllocatePoolWithTag`，是"枚举 → 附体 → 读 → 比对"的完整链条。

### 2.5 针对完整性校验

`.rdata` 里有 `SHA224` / `SHA256` 字符串与常量表，`.text` 有 31 处 `KeBugCheckEx`（校验失败即蓝屏）。校验对象有两种可能：

| 可能对象 | 判定依据 | 应对 |
|---|---|---|
| 自身镜像（`.text`/`.tvm0` 段哈希） | 段基址 + `SizeOfImage` 常量在代码里出现 | 任何 patch 必须**同时**改校验值，或 hook 校验函数 |
| 关键内核结构（`SSDT`/`IDT`/`HalDispatchTable`/`ntoskrnl` 代码段） | 6 个函数引用 `HalDispatchTable`，`MmGetSystemRoutineAddress` 解析 `KeServiceDescriptorTable` 类符号 | 用 `KernelBase` 重定位后的真实地址做"影子"读，或恢复被 hooks 的字节 |

因为文件本身被 WHCP 签名覆盖（`FORCE_INTEGRITY`），**磁盘 patch 一定加载失败**；可行路径只有：
1. 运行时改内存（页表改只读属性 / `CR0.WP` 清除 / `MmMapIoSpace` 映射物理页直写），且必须让校验函数读到"原值"（典型做法：校验时临时恢复、校验后再改回，即 double-map：数据页两个虚拟映射，一个真一个假）。
2. Hook 校验函数本身（`0x61DC6` 派发链上的 `sub_1FC80` 是 `sub_165F0` 的前置校验点，形状类似通用 "is allowed" 检查）。

### 2.6 反混淆：把 `.tvm0` 变白盒

`.tvm0` 不是字节码虚拟机，而是**明文原生 x86-64 + 平坦化**（熵 6.0，`0x4A800` 起可直接看出 `lea rsp,[rsp-0x278]` 这类正常序言）。所以不需要解密器，只需要：

1. 静态：`tools/trace.py` 已能折叠 975 处计算型跳转，恢复真实 CFG：
   ```powershell
   python tools\trace.py 6cf71 400        # IOCTL 入口
   python tools\trace.py 61dc6 4000       # 派发器
   ```
2. 动态：`cdb -k` 附加内核调试，在 `0x140061DC6` 下断点，`uf` 反汇编当前块；由于代码是明文的，`u` 直接出真指令。
3. 若要枚举"信封内操作码"：在 `sub_2E780`（`memset`）之后的 `mov edx,[rbx+0x24]` 处下断，观察 `[rbx+0x28]` 附近的 switch 值。

> 这一步是"能否做出可靠的绕过"的前提：不清楚内部操作码，就只能做粗粒度的整体拒绝（2.1/2.2），做不到精细欺骗。

## 3. 组合策略（按成本排序）

| 方案 | 组成 | 达成目标 | 施工量 | 稳定性 |
|---|---|---|---|---|

## 4. 失败模式清单（踩了就蓝屏/被抓）

| 触发点 | 现象 | 规避 |
|---|---|---|
| 改 `.text` 字节且未处理签名/完整性 | 加载失败（`STATUS_INVALID_IMAGE_HASH`） | 只在内存改，且让校验读到原值 |
| 让 `g_OpenCount` 与 `g_InFlight` 不一致 | CLOSE 时断言/`KeBugCheckEx` | 成对维护两个计数器 |
| 设备对象被删除但符号链接未删 | 下次 CREATE 返回 `STATUS_OBJECT_NAME_NOT_FOUND`，ACE 侧判定异常 | 用 `IoDeleteSymbolicLink` 再 `IoDeleteDevice` |
| 摘 `ActiveProcessLinks` 后未修 `UniqueProcessId` 哈希表 | 句柄表/`PsLookupProcessByProcessId` 崩 | 同时修 `PspCidTable` 或干脆不摘链 |
| 摘 `KBUGCHECK_REASON_CALLBACK_RECORD` 时链表正在被遍历 | 蓝屏 | 持 `KeBugCheckReasonCallbackListHead` 锁（`nt!KeBugCheckReasonCallbackListLock`）后操作 |
| 在 `.tvm0` 上打补丁但没考虑 `0x124000` 异常表 | 异常分发到错误 unwind 信息 → 蓝屏 | 补丁不要跨越登记过的函数边界 |

## 5. 还没做完的事（要拿"完整绕过方案"必须补）

1. **信封内操作码表**：`0x61DC6` 的分支只处理了外层 3 个 IOCTL；内部命令枚举需要完整执行/模拟 `sub_2E780` 之后的解析（字段 `[rbx+0x24]` 起的结构）。这是 S3/S5 的前置条件。
2. **加密字符串表**（`0x2F3B0` 起）：解出后能得到"它要检测的进程名/模块名/注册表路径"清单，直接决定 S4 的优先级。
3. **`0x63C29` 那 28.6 KB 的进程处理函数**：这是"枚举 → 附体 → 读内存 → 比对"的主循环，需要按 975 条边重建 CFG 后逐块翻译（工作量约 3–5 天）。
4. **用户态侧**（`ACE-Service64.exe` / `SGuard64.exe` / `ACE-Tray.exe`）：驱动只是执行端，检测策略与上报在用户态；只改驱动不改策略，ACE 仍可能从用户态侧发现异常。

> 说明：本报告的每一项都对应可复现的静态证据（RVA + 字节），没有推测性结论混在里面；标注"推断"的段落已显式写明。第 5 节的三项是**未完成**部分，不作为已结论使用。
